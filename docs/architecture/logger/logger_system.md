# 统一日志系统

## 一、最初动机：为了调试并发压测的可观测性

> 出发点：建立可观测性（Observability）

- 需要观察订单提交
- 需要观察撮合事件
- 需要分析并发压测过程中的行为

但一开始没有区分：

- 调试日志
- 运行时日志
- 性能路径

为后续问题埋下了隐患

## 二、第一版日志实现的核心问题

实现的函数 `PrintLog(isConsoleLog, message, filePath)` 把文件系统操作放在高频业务路径中，在每次调用都会：

- `MkdirAll`
- `OpenFile`
- `WriteString`
- `Close`

从而在高并发压测下导致：

- `syscall` 大量堆积
- 文件句柄频繁打开关闭
- 内核锁竞争
- goroutine 排队
- test 超时

这是严重架构级错误，违反了**热路径设计原则**

## 三、热路径污染问题

错误地将日志写入操作直接放入撮合系统的核心热路径中，如：

- `Engine.Submit`
- `SymbolMatcher.matchAndEmit`

这些是：

> 核心路径必须满足：

- 无 IO
- 无外部依赖
- 无重锁
- 无阻塞
- 常数级操作

如果在这里加入：

- 文件 IO
- `log.Println`（内部有锁）
- 字符串拼接

则会直接破坏了吞吐上限

## 四、并发系统中的 IO 放置原则

在事件驱动架构中，正确的 IO 架构：

> ```
> 业务线程 → channel → 日志线程 → 文件
> ```

而不是：

```
业务线程 → 文件
```

正确的模型必须：

- 单 goroutine 写文件
- 复用文件句柄
- 有缓冲 channel
- 支持优雅关闭

否则日志会成为吞吐瓶颈

## 五、异步日志的必要性

在高频交易或撮合系统中，**日志的优先级永远低于撮合**。日志可以丢，但订单不能丢。

为避免日志系统会反向控制撮合系统， **`Log()` 必须非阻塞**

## 六、潜在未解决问题

即使改为异步 logger，仍需注意：

1. channel 容量是否合理
2. 是否统计丢日志数量
3. 是否在 Stop 时 drain channel
4. 是否存在 goroutine 泄漏
5. 是否存在格式化开销过大
6. 是否在高频路径做 fmt.Sprintf

很多系统在 `fmt.Sprintf` 时就已经损失大量 CPU
