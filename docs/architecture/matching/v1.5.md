### 现有系统不足

#### 1. Engine Stop 阻塞

最初问题：

```
matcher.Submit 阻塞
wg.Wait 永远等不到
```

原因：

* matcher 内部 channel 满
* Submit 是阻塞写
* Engine goroutine卡死

这是典型的“上游被下游背压锁死”

通过改为：

```
select { case ch <- order: default: }
```

避免了死锁。

但引入新风险——潜在丢单（未统计）

#### 2. eventCh 无消费者导致死锁

当混合撮合后：

* eventCh 写满
* matcher goroutine 卡在发送
* Stop 等待 matcher 退出
* test 超时

根因：

> 生产者存在，但消费者未启动

这是架构完整性问题，不是代码 bug。

你学到的关键原则：

> 任何 channel 都必须明确消费能力。

#### 3. 日志系统注入 IO 的致命影响

后来加入：

```
OpenFile + Write + Close
```

直接进入撮合路径。

结果：

* IO syscall
* 文件锁
* goroutine 排队
* test 超时

这是最关键的工程教训**不能在热路径加入磁盘 IO**

撮合核心路径必须：

* 内存操作
* 无阻塞
* 无外部资源依赖

#### 4. 背压（Backpressure）问题的暴露

测试报错`超时`，原因是**生产速度 > 消费速度**

具体表现为：

1. matcher orderCh 满
2. eventCh 满
3. 日志 IO 阻塞

现在系统缺失：

* 背压统计
* 丢单计数
* 动态流控
* 限速策略

这属于下一阶段问题。

#### 5. 压测方法学上的不足

目前的测试：

* 没有统计成交数量
* 没有统计丢单数量
* 没有统计 event 数量
* 没有统计 goroutine 数量
* 没有持续压测（60s+）
* 没有 CPU profile
* 没有内存 profile

因此，测试只能说明“不崩溃”，不能说明“高性能”

### 潜在坑点

1. Submit 默认丢单未统计
2. eventCh 容量未评估
3. Stop 顺序依赖消费者是否存在
4. 单 symbol 热点风险
5. 日志系统可能仍然丢失关键信息
6. 未进行多 symbol 横向扩展测试
7. 未进行长时间稳定性测试
8. 未考虑 GC 影响
9. 未测内存增长曲线

## 接入统一日志系统

### 调用

分别在：

- `internal\matching\engine.go` 的 `Submit` 方法
- `internal\matching\symbol_matcher.go` 的 `matchAndEmit` 方法
- `internal\matching\matcher.go` 的 `Match` 方法

中调用日志系统的 `Log` 方法

### 关闭

在 `internal\matching\engine.go` 的 `Stop` 方法中调用日志系统的 `Close` 方法

### 日志输出目标

在项目根目录下创建 `/log` 目录，其下的 `/engine` 专用于接收撮合引擎日志
