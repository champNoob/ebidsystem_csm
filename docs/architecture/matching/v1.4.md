# 撮合引擎-1.4

## 多协程撮合引擎

### 当前版本的订单提交流程

```txt
CreateOrder
  → matcher.Submit(order)
      → engine.orderCh (单一 channel)
          → Start() goroutine
              → 按 symbol 找 OrderBook
              → ob.AddOrder
              → ob.Match
```

#### ✅ 优点

- 全局只有一个 goroutine 在撮合
- 所有 symbol 共用一个 orderCh
- 当前阶段不会出现数据竞争

#### ❌ 致命问题

- 所有 symbol 共用一个撮合循环
- AAPL 的高频撮合会阻塞 BTC、ETH
- 无法并行扩展
- 多核 CPU 完全浪费
- 未来一旦加事件回写 DB（Fill / Trade）
- 会被一个慢 SQL 拖死所有 symbol
- 逻辑上不符合真实交易所模型

> 真实世界的 symbol 是**天然隔离**的撮合单元

所以必须做 **symbol 级串行**，而不是全局串行

### 目标架构

在引擎（Engine）和订单簿（OrderBook）之间，引入股票代码级（symbol 级）的撮合器 **symbol_matcher**，
使得 `OrderBook` 不再被 Engine 直接操作，而是由 `symbol_matcher` 统一管理。

```txt
CreateOrder
   |
   v
Engine.Submit(order)
   |
   v
dispatcher goroutine
   |
   +── AAPL matcher goroutine (串行)
   |
   +── BTC matcher goroutine (串行)
   |
   +── ETH matcher goroutine (串行)
```

```txt
                ┌──────────────┐
Submit ───────▶│   Engine     │
                │              │
                │ map[symbol]  │
                │   ↓          │
                │ SymbolMatcher│
                │   ↓          │
                │ OrderBook    │
                │              │
                │ eventCh ◀───┴── MatchEvent
                └──────┬───────┘
                       │
                       ▼
             OrderService.StartMatchEventListener
```

### 最终职责划分

#### Engine

> 全局调度器

- 只负责：

    - 接收订单（Submit）
    - 按 symbol 路由订单
    - 汇总撮合事件（event fan-in）

- 不应该：

    - 直接调用 OrderBook.AddOrder / Match
    - 理解撮合细节
    - 处理并发细节

#### `SymbolMatcher`（核心）

> `symbol` 级串行执行单元，撮合串行化模型的**实体承载者**

- 职责：

    - 一个 `symbol` = 一个 `goroutine`
    - 串行处理该 `symbol` 下的：新订单、撤单等功能
    - 内部持有：一个 `OrderBook`、一个私有的 `orderCh` / `cancelCh`
    - 将撮合结果推送到 Engine 提供的 `eventCh`

#### OrderBook

> 纯内存数据结构，应该是完全“傻”的对象

- 职责：

    - 维护买卖盘
    - 执行撮合算法（Match()）

- 不关心：

    - 并发
    - goroutine
    - channel
    - 数据库
    - Engine

### 主要更改

#### 1. 添加 `internal\matching\symbol_matcher.go`

- OrderBook 不加锁
- Match() 不加锁

安全性来自**单 goroutine**

#### 2. 重构 Engine：从“全局撮合”变成“symbol 路由器”

- 修改 `internal/matching/engine.go`
- 修改 `NewEngine`
- 修改 `Start()`（核心修改）

#### 3. `symbol_matcher.go` 的撤单功能

- 添加 `removeCh` 用于接收撤单请求
- 在 `Start()` 中的 `goroutine` 中添加 `select` 语句，处理 `removeCh`

## 撮合事件事务化

### 撮合事件处理流程（最终形态）

```txt
SymbolMatcher
  → Match()
      → 生成 MatchEvent（携带 event_id）
          → Engine.eventCh（fan-in）
              → OrderService.StartMatchEventListener
                  → handleMatchEvent
                      → repo.WithTx
                          ├─ FillOrderTx (buy)
                          ├─ FillOrderTx (sell)
                          └─ CreateTradeTx (idempotent)
```

### 设计理念

#### 事务化的必要性

最早的代码（Postman + 手动测试阶段）的**隐性假设**：

* 撮合事件：
  * 一定只会被处理一次
  * 不会重复
  * 不会失败一半
* `DB`：
  * 不会因为网络 / panic / SQL error 中断
* Engine → Service：
  * 事件不会丢、不重放

这些假设在**单机、单线程、演示 demo**里“看起来没问题”，
但在**任何真实交易系统中全部是错的**。

这次不是“给 SQL 包一层 tx”，而是**一次完整的语义升级**

#### 撮合事件的「Exactly-Once Side Effect」

一个 MatchEvent：
* 要么：
  * 买单 + 卖单 + 成交记录 **同时成功**
* 要么：
  * 什么都没发生
* 并且：
  * 无论事件被重复投递多少次
  * DB 状态最多只前进一步

这在分布式系统里叫：

* 事务一致性
* 幂等副作用
* `at-least-once delivery + exactly-once effect`

#### 事件的唯一性，应该由撮合引擎（而非数据库）定义

合理的幂等链路：

```txt
SymbolMatcher
   生成 event_id
       ↓
Engine
       ↓
OrderService.handleMatchEvent
       ↓
repo.CreateTradeTx
       ↓
UNIQUE(event_id)
```

### 主要更改

- `symbol` 级撮合引擎，确保**隔离性**：
  - 同 `symbol` 撮合串行
  - 同一订单不会被并发处理

- 在**服务层**调用仓储层定义好的 `Tx` 函数（`WithTx(ctx,func())`），确保“插入`match_event`”、“扣减买/卖单”、“插入`trade`”等操作全部在一个**原子性**事务中

- 在**仓储层** `FillOrderTx`、`CreateTradeTx` 等函数中：
  - 使用 `ExecContext` 确保 `SQL` 语句的**原子性**
  - 通过**状态判断**确保数据的**一致性**

### 坑点总结

#### 1：只有 Trade 幂等，Order 没幂等

第一次测试暴露了本质问题：

```txt
第二次 apply():
  FillOrderTx 又执行了一次
  Trade 被 unique key 吃掉
  => 订单被多填
```

> 幂等不是“最后一步幂等”，而是**整个事务路径必须幂等**

- 正解：引入「事件处理表」作为事务门闩

```sql
CREATE TABLE match_events (
    event_id VARCHAR(64) PRIMARY KEY
);
```

并在事务**最前面**：

```sql
INSERT INTO match_events(event_id) VALUES (?)
-- duplicate → 直接 return nil
```

这一步的意义是，整个事务是否执行在 DB 层一次性裁决。后续所有操作要么全执行，要么完全跳过

#### 2：在 Service 层做幂等判断

一开始的设计是先在 `handleMatchEvent` 里判断。

但这在**架构上不成立**，因为：

- Service 无法原子判断
- 并发 listener 会失效
- 幂等必须**下沉到 事务 + DB**

## 幂等性检查机制

### 设计理念

#### 撮合事件必须拥有 **稳定唯一的 EventID**

这是整个幂等性的**锚点**：

```go
type MatchEvent struct {
    EventID     string
    BuyOrderID  uint64
    SellOrderID uint64
    Price       float64
    Quantity    int64
}
```

**结论：**

* EventID ≠ TradeID
* EventID 是：

  * “这一次撮合动作”的身份
  * 可重放、可去重

#### 幂等不是靠「先查有没有」，而是靠 **数据库唯一约束**

是正确路线：

```sql
trades.event_id UNIQUE
```

而非：

```go
SELECT * FROM trades WHERE event_id = ?
```

因为：

* `SELECT` + `INSERT` ≠ 原子
* 并发下会双写
* 唯一索引是数据库级别的**并发裁判**

真正的事务边界：**以 MatchEvent 为单位**

> 一个 `MatchEvent` = 一个 DB 事务

事务里必须**同时**包含：

* 买单 `Fill`
* 卖单 `Fill`
* 成交记录 `Insert`

### 主要更改

- 使用 `InsertMatchEventTx` 实现事件去重

- 设置 `trade` 表的 `UNIQUE(event_id)`

### 测试

#### 1. TestHandleMatchEvent_Idempotent

- 测试目标：验证**同一个 MatchEvent 执行 N 次，效果 = 执行 1 次**

- 测试方式：

  - 同 `eventID` 调用两次 `apply()`
  - 断言 `trades == 1`
  - 断言 `buy.filled_quantity == 10`
  - 断言 `sell.filled_quantity == 10`

- 验证内容：

  - DB 唯一约束
  - 事务入口幂等
  - Order 更新不会被重复执行

- 测试方式：多次将 `ev` `append` 进 `events` 中，验证 `apply` 的结果一致
